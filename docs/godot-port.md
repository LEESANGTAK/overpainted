# Godot 이식 계획 (2026-11-26)

엔진은 Godot으로 정했다 (디자이너, 2026-11-26). 메커니즘은 더 늘리지 않고, 데모 수준으로 완성도를 올린다. 이 문서는 지금의 브라우저 프로토타입을 Godot으로 옮기는 순서다.

## 한 줄 요약

**규칙과 레벨은 그대로 옮기고, 화면과 연출은 새로 만든다.** 레벨 설계 도구(에디터, 풀이기, 생성기, 예측기)는 지금의 웹·Node 쪽에 남긴다. Godot은 플레이어가 하는 게임만 맡는다.

## 정한 것 (제안)

| 항목 | 제안 | 이유 |
|---|---|---|
| 버전 | **Godot 4.7.2** (2026-11-26 고정, 디자이너). 데모까지 올리지 않는다. 지금 PC의 4.7.2는 Steam판이라 자동 업데이트를 꺼 두어야 한다. | 중간에 엔진 버전이 바뀌면 원인 모를 차이가 생긴다. |
| 언어 | **GDScript** | 지금까지 Godot 4에서는 C# 프로젝트를 웹으로 내보낼 수 없다 (시작할 때 다시 확인). 테스트 링크(웹)를 계속 쓰려면 GDScript여야 한다. 규칙 코드가 작아서(규칙 약 500줄, 풀이기 약 230줄) 속도 걱정도 없다. |
| 저장소 | 같은 저장소의 `godot/` 폴더 | 레벨 JSON과 규칙 테스트를 한곳에서 맞춘다. |
| 기준 화면 | 1280×800 (16:10, Steam Deck) | 가장 중요한 기기에 맞추고, 16:9 PC와 웹은 여백으로 맞춘다. |
| 내보내기 | 웹(테스트 링크) · Windows · Linux(Steam Deck) | 웹은 스레드 없는 내보내기로 GitHub Pages에 그대로 올린다 (Godot 4.3부터 가능). |
| 레벨 설계 | 지금처럼 웹 에디터와 `tools/*.mjs` | Godot으로 옮기지 않는다. 레벨 파일만 넘긴다. |

## 옮기는 것과 옮기지 않는 것

**옮긴다 (게임 안에서 필요)**
- 규칙: 시선, 타격, 두 겹, 밑칠, 혼색, 원본, 테이프, 팔레트 (`core/rules.js`)
- 작은 풀이기: "지금 상태로 깰 수 있는가"와 "가장 좋은 다음 수" (`core/solver.js`의 일부). 힌트와, 판이 조용히 틀어졌을 때의 음악·마르는 캔버스(`noteBlunder`)에 필요하다. 레벨마다 상태가 수백 개라 게임 안에서 바로 풀어도 충분히 빠르다.
- 레벨 데이터: `levels/prototype.json` (장, 레벨, 이름·안내의 한국어/영어, 기준 수)
- 입력: 마우스, 터치(끌어 놓기 포함), 게임패드 (`prototype/pad.js`의 커서, X 도구 휠)
- 화면: 장·레벨 고르기, 판, 도구 트레이, 결과, 설정
- 소리: 두 곡을 함께 틀고 천천히 넘기는 음악 (`prototype/mood.js`), 효과음
- 저장: 레벨별 최고 기록, Extra 잠금 해제, 소리·언어 설정
- 플레이테스트 기록: 지금 Google 시트 수집기로 그대로 보낸다 (테스트 빌드에서만 켠다)

**옮기지 않는다**
- 레벨 에디터, 분석 패널, 풀이 다시 보기 (개발용)
- 리터칭, 나누기 (메인 코스에서 뺀 규칙)
- 레벨 생성기, 본능 예측기, 난이도 측정 (Node 도구로 남는다)
- 지금의 그림 (코드로 그린 임시 그림이다. 아트 단계에서 새로 그린다)

## 규칙이 두 벌이 되는 위험

규칙이 JS(설계 도구)와 GDScript(게임)에 따로 있게 된다. 한쪽만 고치면 레벨의 기준 수나 난이도가 게임과 어긋난다. 그래서 **같은 답을 내는지 자동으로 맞춰 본다.**

- `tools/parity.mjs` (새로 만듦): 실제 레벨과 무작위 판에 대해 "이 수들을 두면 이 상태가 된다, 이 상태는 깰 수 있다/없다, 최소 몇 수"를 JS로 계산해 `godot/tests/vectors.json`에 쓴다.
- Godot 쪽 테스트(`godot --headless`로 실행)가 같은 벡터를 GDScript 규칙으로 돌려 한 줄이라도 다르면 실패한다.
- 규칙을 고칠 때는 JS 먼저, 그다음 GDScript, 그다음 두 테스트가 모두 통과해야 끝난다. 메커니즘을 더 늘리지 않기로 해서, 이런 일은 드물 것이다.

## 단계

각 단계는 "끝났다"를 확인할 수 있는 기준이 있다. 크기는 상대적인 어림(S 작음 · M 보통 · L 큼)이다.

### 0. 뼈대 (S)
- `godot/` 프로젝트, 버전 고정, 기준 화면과 늘림 방식.
- 레벨 파일을 넘기는 스크립트: `tools/export-godot.mjs`가 `levels/prototype.json`에서 게임에 필요한 것만 `godot/data/levels.json`으로 옮긴다 (난이도 수치는 뺀다).
- 한글 글꼴을 넣는다. Godot 기본 글꼴에는 한글이 없다. 무료로 넣을 수 있는 글꼴(예: Noto Sans KR, Pretendard)을 고르고 라이선스를 확인한다.
- **끝:** 빈 화면이 웹과 PC에서 뜨고, 한글이 보인다.
- **끝냄 (2026-11-26):** `godot/` 프로젝트(4.7.2, Compatibility 렌더러, 1280×800), `tools/export-godot.mjs` → `godot/data/levels.json` (9장 48판, 데모 5장 메인 25판, `npm test`가 최신인지 확인), Noto Sans KR(굵기 400). 4.7.2 내보내기 템플릿을 설치하고(공식 SHA512 확인) `godot/export_presets.cfg`에 웹(스레드 없음)·Windows·Linux를 두었다. 웹 빌드는 브라우저에서, Windows 빌드는 실행해서 한글과 레벨 수가 뜨는 것을 확인했다. 크기: 웹 46MB(wasm 39MB + pck 6.8MB), Windows 116MB, Linux 80MB.
- **남은 것:** Linux 빌드를 Steam Deck에서 실행해 보기 (이 PC에서는 못 돌림), 글꼴 OFL.txt 넣기, 웹용 글꼴 줄이기(출시 전).
- 내보내기: `godot --headless --path godot --export-release Web` (또는 `Windows`, `Linux`). 결과는 `godot/build/` (git에 올리지 않음, `.gdignore`로 Godot도 읽지 않음).

### 1. 규칙 이식과 맞춰 보기 (M)
- `rules.gd`: 판 읽기, 시선(probe), 타격, 두 겹·밑칠·혼색·원본, 테이프, 팔레트(덜어 오기 포함), 이김·짐 판정.
- `solver.gd`: 깰 수 있는가, 최소 수, 다음 좋은 수. (난이도 수치는 계산하지 않는다.)
- `tools/parity.mjs`와 Godot 테스트.
- **끝:** 모든 메인·Extra 레벨과 무작위 판 수백 개에서 JS와 GDScript가 같은 답을 낸다.
- **끝냄 (2026-11-26):** `godot/scripts/core/rules.gd`, `solver.gd`. 타일 번호와 상태 배열이 JS와 같아서 상태를 바이트 단위로 비교한다. `tools/parity.mjs`가 실제 48판 + 무작위 140판(밑칠, 혼색, 원본, 테이프, 팔레트, 벽 포함)에서 무작위로 둔 1,512개 상태의 정답(칸마다 시선, 타격 목록, 도구 수, 팔레트 색, 이김·짐, 풀이기 답과 풀이)을 쓰고, `godot/tests/run_tests.gd`가 56,221개를 확인한다. 모두 같다. 일부러 규칙과 풀이기에 버그를 넣어 보면 테스트가 잡는다.
- 실행: `npm run test:godot` (빠르게: `npm run test:godot -- quick`, 풀이기 확인을 건너뜀). Godot 경로는 `GODOT` 환경 변수, 없으면 Steam 설치 위치.
- 풀이기 속도: 게임은 수를 둔 뒤 "아직 깰 수 있는가"를 계산한다. 처음 옮긴 그대로는 「조각 10」 시작에서 675ms라 화면이 멈칫했다. JS의 `movesFast`처럼 시선 줄을 미리 만들고 상태마다 칸 표를 한 번만 만들어 99ms로 줄였다 (`godot/tests/bench.gd`). 타격 애니메이션(280ms) 동안 계산하면 보이지 않는다.
- 옮기지 않은 것: 리터칭과 나누기, 난이도 수치(무작위 성공률 등)와 "원본만 피하는 플레이어" 모드, 판을 글자로 바꾸는 함수들(`toRows` 등, 에디터용).

### 2. 회색 판으로 끝까지 (M)
- 판 그리기(임시 도형), 타격과 벗겨짐, 시선 미리 보기, 되돌리기, 처음부터, 이김, 별.
- 도구: 테이프, 팔레트(놓을 수 있는 칸 표시, 덜어 올 타일 고리, 벗겨지는 애니메이션).
- 원본이 상했을 때의 상태(되돌리기만 가능).
- **끝:** 아무 레벨이나 열어 마우스로 끝까지 깰 수 있다. 결과가 프로토타입과 같다.
- **진행 (2026-11-26):** 회색 판 플레이 화면 (`godot/scripts/game/play.gd`, `board_view.gd`). 타격(헛치면 깜빡임), 벗겨지는 애니메이션(280ms, 맞은 시선과 고리), 마우스를 올리면 시선 미리 보기, 되돌리기(Z), 처음부터(R), 이김 카드(별, 다시, 다음·다음 장), 원본이 상했을 때와 더 칠 곳이 없을 때의 알림, 개발용 레벨 고르기(PgUp/PgDn). 타일: 두 겹은 테, 밑칠은 아래 색 고리, 혼색은 반반, 원본은 칙칙하게 금, 옛 테이프는 X.
- 확인: `godot/tests/play_test.gd`가 도구 없는 35판을 실제 화면에서 풀이대로 한 칸씩 눌러 끝까지 깬다. 모두 기준 수에 이기고, 이긴 뒤 되돌리기와 처음부터도 맞다 (`npm run test:godot`에 들어 있음).
- **남은 것:** 테이프와 팔레트 조작 (데모에 없어서 뒤로 미룸: 7·8·9장과 6장), 시선 미리 보기 켜고 끄기(4단계 설정).

### 3. 입력 세 가지 (M)
- 마우스(지금과 같음), 터치(끌어 놓을 때 조각이 손가락 위에 뜨는 것까지), 게임패드(커서, A 타격, B 되돌리기, X 도구: 짧게 = 마지막 도구, 누른 채 = 휠, Y 힌트, LB/RB 레벨).
- Godot의 입력 설정(Input Map)으로 묶어, 키보드와 패드가 같은 동작을 부른다.
- **끝:** Steam Deck에서 터치만으로, 패드만으로 각각 한 장을 끝까지 깰 수 있다.
- **진행 (2026-11-26):** 입력 동작을 `godot/scripts/input/controls.gd`에 모았다 (키보드와 패드를 같은 이름에 묶음, 프로토타입의 패드 배치). 커서: 십자키·방향키·왼쪽 스틱(센 축이 이김), 누르고 있으면 260ms 뒤부터 110ms마다 한 칸, 판 끝에서 멈춤. 첫 입력은 커서만 보인다 (프로토타입은 첫 A에도 쳤는데, 보이지 않는 커서로 치지 않게 바꿨다). 마우스나 터치를 쓰면 커서가 사라진다. A 두드리기, B 되돌리기, View 처음부터, LB/RB 그림. 결과 카드에서는 십자키로 단추를 고르고 A로 누른다. 아래 안내 줄이 키보드/패드에 맞게 바뀐다. 터치는 Godot이 클릭으로 바꿔 주어 그대로 된다.
- Godot 4.7의 기본 UI 동작(`ui_accept`, `ui_left` 등)에는 패드가 들어 있지 않다. 그대로 두면 결과 카드에서 A가 먹지 않아서, 패드 A와 십자키·스틱을 더했다.
- 확인: `godot/tests/input_test.gd`가 실제 입력 이벤트로 **패드만으로 데모 25판을 처음부터 끝까지 이어서** 깨고 (결과 카드 A로 다음 판, B로 되돌리기, LB/RB 포함), **터치만으로 25판**을 깬다. 모두 통과.
- **남은 것:** Steam Deck 실기에서 확인 (Steam 입력 설정, 터치 화면). 도구(X)·힌트(Y)·소리(Menu)는 그 기능이 생길 때.

### 4. 게임의 틀 (M)
- 장·레벨 고르기 화면 (Rail Bound 같은 지도형은 아트 단계에서. 지금은 목록이어도 된다).
- 저장(`user://`), Extra 잠금 해제, 다음 레벨·다음 장으로 넘어가기.
- 한국어/영어: 레벨 이름과 안내는 레벨 파일에서, 화면 글자는 Godot 번역 파일로.
- 설정: 소리, 언어, 시선 미리 보기 켜고 끄기.
- **끝:** 처음 켜서 데모 범위를 처음부터 끝까지 이어서 할 수 있고, 껐다 켜도 기록이 남는다.

### 5. 분위기와 알림 (S–M)
- 음악 두 곡을 함께 틀고 천천히 넘기기, 저역 필터 (지금 `mood.js`와 같은 시간·크기). Godot의 오디오 버스로 만든다.
- 판이 조용히 틀어지면 몇 수 뒤(또는 몇 초 뒤)에 음악이 바뀌고 캔버스가 마른다. 바로 알려 주지 않는다는 규칙은 그대로.
- 힌트.
- **끝:** 프로토타입과 같은 때에 같은 느낌으로 바뀐다 (디자이너가 나란히 놓고 비교).

### 6. 테스트 빌드 (S)
- 플레이테스트 기록을 지금 시트 수집기로 보낸다. 기록 형식은 지금과 같게 해서 `tools/playtest.mjs`를 그대로 쓴다. 기록에 `engine: "godot"`을 붙여 프로토타입 기록과 구분한다.
- 테스터 이름 받기, 첫 안내.
- 웹 빌드를 GitHub Pages에 올린다. 프로토타입 링크와 주소를 나눌지 정한다 (예: `/overpainted/` 는 Godot, `/overpainted/prototype/` 은 그대로).
- **끝:** 링크 하나로 테스트하고, 기록이 시트에 쌓이고, 분석 도구가 읽는다.

### 7. 데모 완성도 (L, 별도 계획)
여기부터는 이식이 아니라 새 작업이다. 이식이 끝난 뒤 따로 계획을 세운다.
- 아트: GOROGOA 같은 결의 그림 (`docs/later.md` 2). 타일, 테이프, 혼색, 원본, 마르는 캔버스를 그 결로.
- 연출: GRIS처럼 말 없이 전하는 연출. 벗겨질 때의 빛과 색, 장이 끝날 때 그림이 드러나는 순간.
- 장·레벨 고르기 지도, 효과음, 진동(패드).
- Steam: 데모 페이지, Steamworks 연동(GodotSteam 등), Steam Deck 검증.

## 정한 것: 데모 범위 (2026-11-26, 디자이너)

**데모는 1~5장**: 용제, 방패, 두 겹, 밑칠, 혼색. 메인 25판에 3장의 Extra 「조각 10」, 1시간 남짓. 메커니즘이 하나씩 늘어나는 맛을 보여 주고, 팔레트·테이프·원본(8장의 반전)은 본편을 위해 남긴다.

- 그래서 이식 순서도 데모 범위부터: 2단계(회색 판)의 도구 중 테이프와 팔레트는 데모에 없으니, 규칙(1단계)은 모두 옮기되 화면 작업은 데모 범위를 먼저 끝낸다.
- 데모의 마지막(혼색 장 「서로가 아니다」) 뒤에 본편을 기대하게 하는 끝맺음이 필요하다 (7단계에서).

## 디자이너가 정할 것

1. **프로토타입의 역할.** 이식 뒤에도 레벨 설계와 빠른 실험은 프로토타입에서 한다 (제안). 그러면 프로토타입의 화면은 더 다듬지 않는다.
2. **테스트 링크.** 이식 중에도 내일처럼 프로토타입으로 테스트를 계속할지, Godot 웹 빌드가 되면 그쪽으로 옮길지.

## 순서에 대한 의견

- 1단계(규칙과 맞춰 보기)를 가장 먼저, 가장 꼼꼼히 한다. 여기서 어긋나면 뒤의 모든 단계가 흔들린다.
- 2~6단계는 그림 없이 한다. 회색 판으로 프로토타입과 똑같이 놀 수 있게 된 뒤에 아트를 얹는다. 그림을 먼저 하면 규칙과 입력 문제를 그림이 가린다.
- 이식하는 동안에도 내일 같은 플레이테스트 결과로 레벨은 계속 고친다. 레벨은 JSON으로 넘기니 이식 작업과 부딪히지 않는다.
